Turning a 1980s Atari ST game binary back into readable, provably-correct C

This workspace recovers lost source from an Atari ST program: it parses the executable, disassembles the 68000 code, drives Ghidra to decompile it, iteratively names everything until it reads like source — then reconstructs clean C and proves each function still matches the original machine code, byte for byte. Buggy Boy is the fully-worked reference example.

01What this is

There is no source code for these old games. They shipped as compiled binaries — and in Buggy Boy's case, hand-written 68000 assembly. The goal is reverse engineering: recover human-readable, named, decompiled code from nothing but the shipped bytes, and be able to trust that recovery.

The project has three parts that stay reusable across any GEMDOS .PRG:

PartWhat it holds
tools/Game-agnostic tooling: a stdlib .PRG parser + 68000 disassembler, Ghidra loader/annotator scripts (Java), depackers, a graphics/sprite extractor, and the shell scripts that drive the naming loop.
docs/Transferable knowledge, one file per domain (binary formats, 68k asm, Ghidra, OS calls, hardware, graphics, sound, methodology). Grounded in Buggy Boy but written as general procedure.
projects/Per-game work: buggyboy/ (solved reference) and joust/. Each has its binary, name map, decompiled C, and Ghidra project.
Two truths that shape everything. (1) The relocation table is gold — honor it on load and every absolute pointer resolves to a real, navigable address, which is what lets Ghidra discover functions. (2) Games bypass the OS — expect file I/O through GEMDOS and everything else through direct hardware, Line-A, and XBIOS. The GUI (GEM) usually shows up only during start-up.

02The Atari ST platform — what makes it specific

The Atari ST (1985) is a Motorola 68000 machine: a 16/32-bit CPU, big-endian, with a flat address space and memory-mapped I/O. Its OS is TOS, and its GUI layer is GEM. Three platform facts drive almost every RE decision:

Everything is memory-mapped

There are no I/O ports. The video shifter, the sound chip, timers and the keyboard controller all live at fixed addresses in the $FFFF8xxx/$FFFFFxxx range. A routine that writes $FFFF8240 is a palette routine — no ambiguity.

The OS is reached by trap, not by call

TOS/GEM have no linked entry points to rename. Code enters the OS with a trap #N instruction and a function selector; the selector picks the specific call. So you identify call sites, not symbols.

Frame-driven by the VBL

A 50/60 Hz vertical-blank interrupt drives per-frame work. Games chain a handler onto the VBL queue (low memory 0x456); whoever installs it owns the tick — often the sound/music driver.

Planar graphics + double buffering

Low-res is 320×200, 16 colours, stored as 4 word-interleaved bitplanes (32000 bytes). Smooth motion = two screen buffers, flip the base address each frame.

The I/O map (the parts games actually touch)

RangeChip / roleNotable registers
$FFFF8200–8260Video / Shiftervideo base hi/mid, sync mode, 8240–825E = 16 palette words, resolution
$FFFF8800/8802YM2149 PSG (sound)write reg # then value; also reads joystick/keyboard via ports A/B
$FFFFFA00–FA2FMFP 68901timers A–D, interrupt enable/mask, GPIP
$FFFFFC00/FC02IKBD ACIAkeyboard / mouse / joystick controller

Palette words are ST 0x0RGB (3 bits/channel). Supervisor mode (via GEMDOS Super or XBIOS Supexec) is needed to touch most of this hardware. There is also Line-A: opcodes $A000–$A00F that trap into fast built-in graphics primitives (put pixel, draw sprite, copy raster) — treat an $A0xx word as a call, not data.

03The GEMDOS .PRG binary format

Before you can disassemble anything, you parse the executable. An ST program (.PRG, .TOS, .TTP) opens with a 28-byte big-endian header. The magic word is 0x601A — literally a bra.s +26 instruction.

OffSizeFieldMeaning
0x002magic0x601A
0x024text lengthcode segment
0x064data lengthinitialized data (often merged into text)
0x0A4bss lengthzero-init region (not stored in file)
0x0E4symbol table length0, or a DRI symbol table
0x1A2absflagif non-zero, no relocation

File layout: header(28) | TEXT | DATA | SYMBOLS | RELOC-TABLE. The code is position-independent: it can load anywhere, and the relocation table lists the offsets of every 32-bit longword that must have the load base added.

Why the reloc table is the single biggest lever. Load a .PRG as a flat blob and every absolute pointer (lea $xxxx.l, jump tables) is wrong, so Ghidra's analysis finds almost nothing. Apply the relocations — *(u32*)(image+off) += load_base for each fixup — and the whole call graph resolves.

A quick first look with the workspace's own parser:

# prints header sizes, reloc count, embedded strings, first-pass disassembly
python3 tools/prg_dis.py projects/buggyboy/bin/BUGGYBOY.PRG | head -60

Strings alone are worth a lot: Buggy Boy's binary reveals the loaded files ("COURSES.DAT", "GRAPHICS.GRA") and the author credit ("coded by Martin W.Ward"). It also kept 11 DRI symbols — a sound driver's exports (INITTUNE, EGVOL, REFRESH…) that name a whole subsystem for free.

Watch for packing. If the entry point disassembles to garbage and the text entropy is high (> ~6.7, which prg_dis.py prints), the executable is crunched — you depack it (statically, or by running it in the Hatari emulator and dumping memory) before analysis. Joust's .CTE is exactly this case.

04The reverse-engineering pipeline

.PRG binary │ parse header / symbols / relocs ▼ raw import into Ghidra (68000 : big-endian : 32-bit) │ PrgLoader rebuilds TEXT at the load base, applies relocations, │ imports DRI symbols, sets the entry point ▼ auto-analysis + OS-trap annotation │ AtariOsTrapAnnotate labels every trap #1/#13/#14/#2 call site │ ExportDecompC → decomp.c ▼ THE NAMING LOOP (the bulk of the work) read decomp.c → anchor on traps / hardware / strings / symbols → add fn/var/cmt lines to names.txt → reapply.sh → re-read ▼ RECONSTRUCTION (optional, highest-fidelity) rewrite each function as clean C → prove it byte-for-byte equivalent to the original via a differential test

Concretely, per project:

bash tools/new_project.sh mygame path/to/MYGAME.PRG
bash projects/mygame/run.sh          # bootstrap: analyzed DB + decomp.c
# … read decomp.c, add lines to names.txt …
bash projects/mygame/reapply.sh      # apply names + re-export; repeat
Ghidra 12 gotcha. Ghidra 12 dropped Jython, so all loader/annotator scripts are written in Java (tools/ghidra_scripts/*.java) and run headless out of the box. The load base defaults to 0x10000 to keep the image clear of the 68000 vector page — arbitrary, since .PRGs are position-independent.

The name map (names.txt) is the source of truth

One directive per line. Addresses are Ghidra addresses = image offset + load base.

DirectiveEffect
fn 0x<addr> <name>name / define a function
var 0x<addr> <name>label a data address (renames Ghidra's DAT_*)
cmt 0x<addr> <text>plate comment
param / protorename a recovered parameter, or commit a full signature with explicit storage

A trailing # ctx tags a name inferred from call-context rather than a confirmed body read — honest bookkeeping so a guess is never presented as fact.

05The craft: anchors → outward

You never read a 48 KB binary top to bottom. You anchor on ground truth and propagate along the call graph. Sources of ground truth, strongest first:

  1. OS traps — already annotated: "this function Fopens a file / sets the palette."
  2. Hardware register access — $FFFF8240 = palette, $FFFF8800 = sound. Unambiguous.
  3. Imported symbols — any DRI symbols name whole subsystems for free.
  4. Strings — filenames, menu text, author credit, score labels. They pin down loaders, menus, HUD, high-score code.
  5. Interrupt installs — whoever writes the VBL vector (0x456) owns the per-frame tick.
  6. Call graph — name leaf utilities first (a dbf copy loop = memcpy, a masked blit = draw_sprite), then the callers that compose them.
Verify before you name. Position and size are hints, not evidence. In Buggy Boy a function assumed to be read_input turned out to be flip_screen (it wrote the video base); one guessed as show_message was actually add_score (BCD score with carries). A wrong sticky name is worse than FUN_. Read the decompiled body and confirm what it touches.

Each pass makes the next easier: naming a leaf helper makes its callers legible, which unlocks the layer above. "Done" looks like this — main and the frame loop read as pseudocode, every function has a meaningful name, key globals (state, buffers, tables) are labelled, and jump tables and asset formats are documented. For Buggy Boy that's 91/91 functions.

06Reading OS traps and hardware access

Since the OS is reached by trap, you learn to recognize the four vectors and their selectors:

InstructionLayerHow the specific call is chosen
trap #1GEMDOS (files, memory, process)function # pushed as a word: move.w #sel,-(sp)
trap #13BIOS (devices)selector on the stack
trap #14XBIOS (hardware)selector on the stack
trap #2GEM (GUI)d0=200 → AES, d0=115 → VDI; params via a pointer block

Common selectors you meet constantly: GEMDOS 0x3D Fopen, 0x3F Fread, 0x48 Malloc, 0x4B Pexec; XBIOS 0x05 Setscreen, 0x06 Setpalette, 0x1F Vsync, 0x26 Supexec. Games wrap these in thin helpers (move.w #sel,-(sp); trap #1; addq; rts) which the annotator auto-renames, so callers start to read as Fread(...), Setpalette(pal).

A recognizable start-up shape appears in almost every game: an Mshrink prologue (free RAM above the program), then GEM init and bail to hardware — appl_init → graf_handle → v_opnvwk to grab a screen handle, after which the game bangs the hardware directly. Buggy Boy does exactly this.

07Reconstructing readable C

Naming makes the Ghidra output legible, but it's still full of DAT_*, undefined, CONCAT and register artifacts. The reconstruction step rewrites each function as clean, idiomatic C. The design that makes this safe:

A shared, flat memory image

Both the original code and the reconstruction operate on the same big-endian byte image, indexed by real Ghidra addresses — so the game's globals sit at their true addresses. Accessors (be16, be32) read/write it.

Core + glue

Each function has a core (the readable logic, idiomatic C types) and a glue g_<name>(image, regs…) that unpacks the core's inputs from the image at their real addresses and writes results back. The glue is the function's I/O contract.

Example: add_score — from BCD carry asm to readable C

The original adds a six-digit ASCII score with decimal carry, refreshes the HUD copy, and blanks leading zeros. The reconstruction (src/score.c) reads as prose, with the register→memory contract isolated in the glue:

/* Add v to the n-byte big-endian integer at p (binary carry, as 68k add.l/.w). */
static void add_be(uint8_t *p, int n, uint32_t v) {
    uint32_t acc = 0;
    for (int i = 0; i < n; i++) acc = (acc << 8) | p[i];
    acc += v;
    for (int i = n - 1; i >= 0; i--) { p[i] = (uint8_t)acc; acc >>= 8; }
}

void score_add(uint8_t *score, char *score_str, const uint8_t *delta, int game_over) {
    if (game_over) return;
    /* 68k adds the top four digits as one long and the low two as a word. */
    add_be(score,     4, be32(delta));
    add_be(score + 4, 2, be16(delta + 4));
    /* Decimal carry, least-significant digit upward. */
    for (int i = SCORE_DIGITS - 1; i >= 1; i--)
        if ((int8_t)('9' - score[i]) < 0) { score[i] -= 10; score[i - 1] += 1; }
    /* Refresh the on-screen digits, then blank leading zeros ('0' -> '/'). */
    memcpy(score_str + 4, score, SCORE_DIGITS);
    for (char *p = score_str + 4; *p == '0'; p++) *p -= 1;
}

/* Glue / I/O contract: A1 -> 6-byte delta; reads game_over_flag; writes score + score_str. */
void g_add_score(uint8_t *image, uint32_t delta_ptr) {
    int game_over = be16(image + A_game_over_flag) != 0;
    score_add(image + A_score_bcd, (char *)(image + A_score_str), image + delta_ptr, game_over);
}

Note the conventions the code-review gate enforces: no magic numbers (SCORE_DIGITS, named addresses like A_score_bcd), no raw register names in the core, and a one-line comment mapping the register contract in the glue.

08Proving it correct — differential testing

Because Buggy Boy was hand-written assembly, there is no original C to recompile and byte-match against. So correctness is proven a different way: behavioral equivalence. Run the real machine code and the reconstruction on identical starting state, then diff the resulting memory. The emulator is ground truth, so correctness never rests on a human reading being right.

initial memory image + registers │ ┌────────────┴─────────────┐ ▼ ▼ ORACLE (real 68k) CANDIDATE (our C) Musashi via liboracle.so libbuggyboy.so via ctypes │ │ ▼ ▼ final memory + write-set final memory └──────────► diff ◄────────┘ green = byte-for-byte identical

The oracle is Musashi (MAME's 68000 core), chosen because it is faithful to real 68000 behavior. (Unicorn/QEMU's m68k core was tried first and rejected — its ColdFire-derived core raises spurious illegal- instruction faults on byte read-modify-write to memory, which this code does constantly.) The harness diffs the whole image minus a stack-guard band, so any byte the real code writes that the reconstruction gets wrong — or misses — fails the test.

A test looks like this

# Differential tests for add_score @ 0x1580a
def _case(score, delta, game_over):
    pokes = {
        0x1824c: bytes(score),                 # score_bcd + counter
        0x18c34: (1 if game_over else 0).to_bytes(2, "big"),  # game_over_flag
        DELTA_PTR: bytes(delta),
    }
    regs = {"a1": DELTA_PTR, "_pokes": pokes}
    diffs, _ = differential(ENTRY_ADD_SCORE, regs,
                          lambda lib, buf: lib.g_add_score(buf, DELTA_PTR))
    assert not diffs, report(diffs)

def test_fuzz():
    rng = random.Random(12)                 # fixed seed (reproducible)
    for _ in range(3000):                    # full byte range, not just ASCII digits
        score = [rng.randint(0, 255) for _ in range(6)]
        _case(score, [rng.randint(0, 255) for _ in range(6)], rng.random() < 0.1)

Both edge cases (full carry cascade, leading-zero blanking, game-over no-op) and thousands of fuzz cases run through the same oracle-vs-candidate diff. The fuzz domain is deliberately widened to the full byte range — not just the ASCII digits the game ever feeds it — because the disassembly showed a signed cmp.b/bpl carry (and no BCD instruction), so the reconstruction must match the real 68000's sign-extension for every input, not only the reachable ones.

Handling the OS in the oracle. The emulator can't route a trap to real TOS, so oracle/shim.c points each trap vector at a magic PC and services the call deterministically: Malloc bump-allocates, Physbase returns a fixed screen base, Supexec runs the passed routine in place, and Fopen/Fread serve bytes from an in-image staged-file table the harness fills with the real file. Anything not faithfully modeled is counted and raises rather than diff a fabricated result — so a function is only ever marked verified once every OS call it makes is genuinely modeled.
Functions that never return (like _start, whose call into the infinite game loop never comes back) are verified at a checkpoint PC instead of at rts: run the oracle to that address and diff there, excluding the relocated machine-stack band.

Trusting the oracle: validating the validator

The whole method rests on one assumption — the oracle is a faithful 68000, and a green diff really means equivalence. A diff can lie in two ways: the reconstruction might pass by coincidence, or the oracle might be wrong about the hardware. Several layers close those gaps, so a bug can't slip through:

GuardThe loophole it closes
Attribution (poison) passA candidate can match the final image without ever writing a byte the oracle wrote — if that byte already held the oracle's value (an output landing in a zeroed region). The harness re-runs on an image whose oracle-written bytes are pre-poisoned with a canary, so a missed write stays canary instead of coincidentally matching.
Stack-guard write checkThe diff skips the machine-stack band (the pure-C reconstruction has no stack). If the oracle actually wrote program output into that band, the diff would hide it — so any such write fails loudly instead.
Exclude-band vettingCheckpoint verification excludes a relocated-stack band. The harness proves that band really is stack — it reaches the deepest stack pointer the oracle used and covers no named global sitting below the stack — so it can't silently drop a real divergence.
Two-layer OS modelThe deterministic trap shim is (1) pinned at its edges by tiny hand-assembled stub tests, and (2) cross-checked against a real TOS ROM running headless in Hatari. So "Malloc rounds up to even / Fread advances the cursor / Getrez is 0 in low-res" is a checked fact, not a hopeful assumption.
ISA cross-validationMusashi itself is validated against a second, independent 68000 — Hatari's WinUAE-derived core: 277 self-contained instruction snippets (byte/word memory RMW, asr/lsl/rox, ext, muls/divs, addx, cmp.b+Scc) run on both cores and their results + flags compared.
All 277 instruction cases agree. The only divergence the cross-check ever found was N/Z after a DIVS/DIVU overflow — which the 68000 manual declares undefined, so two faithful cores may legitimately differ (it's excluded from the comparison; the result and the defined overflow flag still match). Two independent, hardware-validated cores agreeing is the strongest practical evidence short of real silicon — so "verified against Musashi" is, for Buggy Boy's instruction mix, "verified against a real 68000."

09Buggy Boy, end to end

Buggy Boy (a 1985 arcade racer, ported to the ST by Martin W. Ward) is the fully-solved reference. It exercises every part of the pipeline:

0x601A
the .PRG magic word
  • Loader. Buggy Boy's START.PRG is a tiny launcher — it Fopen/Freads the payload, applies the relocation table by hand, and jumps into it (instead of Pexec) so it can show a title screen first.
  • Start-up. _start does the Mshrink prologue, then GEM init (appl_init → graf_handle → v_opnvwk) and bails to hardware. Verified at a checkpoint just before bsr main.
  • Assets. Strings point at GRAPHICS.GRA and COURSES.DAT; load_graphics / unpack_graphics decode 4-plane sprites, and a jump table drives the course-event engine (collision, gates, flags).
  • Screen. flip_screen toggles a buffer index and writes the video base to $FFFF8200, then Vsyncs — classic double buffering.
  • Score. add_score — the six-digit BCD adder shown above, verified against 2000+ fuzz cases.
  • Sound. The driver's exported symbols (INITTUNE, EGVOL, REFRESH…) name a tune + envelope-generator + effects driver, installed on the VBL queue. Because the real REFRESH runs faithfully in the oracle, you can listen: tap the YM2149 register writes per frame and render them to WAV — revealing that music ids 0–6 are real self-terminating tracks, and effect id ≥ 9 reads zeroed BSS past a 9-record table (so it's silent).
Why the sound story is a good illustration. It shows the whole method compounding: a recovered symbol anchors the subsystem, the hardware map (YM2149 at $FFFF8800) says what each write means, the VBL install says when it runs, and the faithful oracle lets you observe real behavior — down to knowing exactly which effect ids are real versus reading past the table.
